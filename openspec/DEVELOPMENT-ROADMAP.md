## 🎯 Phase 0: 基础设施 (必须线性执行)

### ⚠️ 关键约束

**Phase 0 任务必须严格按顺序执行，不能并行！**

每个任务都依赖前一个任务的产出，任何跳过或并行都会导致后续任务无法进行。

### 执行顺序

```
┌─────────────────────────────────────────────────────────────────┐
│  Phase 0: 基础设施 (68小时，线性执行)                           │
└─────────────────────────────────────────────────────────────────┘

  任务 001: Launcher 开发                    [8h]  ✓ 无依赖
     ↓
  任务 002: Local JAR 服务                   [16h] ← 依赖 001
     ↓
  任务 003: 通信层                           [12h] ← 依赖 002
     ↓
  任务 004: 数据库服务                       [12h] ← 依赖 003
     ↓
  任务 005: 认证系统                         [8h]  ← 依赖 004
     ↓
  任务 006: 插件系统                         [12h] ← 依赖 005
     ↓
  ✅ Phase 0 完成 - 解锁 Phase 1 & Phase 2
```

### 任务详解

#### 📦 Task 001: Launcher 开发 (8h)

**目标**：创建轻量级启动器

**产出**：
- `launcher.jar` (< 20KB)
- 无外部依赖
- 支持热更新和崩溃恢复

**为何第一**：
- 启动器是所有后续组件的引导程序
- 必须先建立可靠的启动机制
- 后续开发中可用于测试主程序的启动和重启

**实施建议**：
1. 第一天上午：创建基础项目结构
2. 第一天下午：实现版本管理和进程启动
3. 第二天：实现崩溃检测和回滚机制
4. 测试：模拟各种启动场景

**验收标准**：
- [ ] 正常启动子进程
- [ ] 崩溃 3 次后自动回滚
- [ ] 更新流程正确执行
- [ ] 跨平台运行 (Windows/Mac/Linux)

---

#### 🔧 Task 002: Local JAR 服务 (16h)

**目标**：开发客户端模式的主程序

**产出**：
- `localverse.jar` (客户端模式)
- HTTP 服务器 (端口 8765)
- WebSocket 服务器 (端口 8766)
- 文件系统服务
- 代理转发能力

**为何第二**：
- 需要 launcher.jar 来启动
- 是整个系统的运行核心
- 为后续通信层提供 HTTP/WebSocket 基础

**实施建议**：
1. 第 1-2 天：项目骨架 + HTTP 服务器基础
2. 第 3 天：WebSocket 服务器 + 文件系统服务
3. 第 4 天：代理转发 + 集成测试

**关键依赖**：
- Java 21
- com.sun.net.httpserver (JDK 内置)
- Java-WebSocket 库
- Gson 库
- SQLite JDBC

**验收标准**：
- [ ] HTTP API 响应正常
- [ ] WebSocket 连接稳定
- [ ] 文件操作正确
- [ ] CORS 配置正确

---

#### 🌐 Task 003: 通信层 (12h)

**目标**：建立浏览器与 Local JAR 的通信机制

**产出**：
- 通信层 SDK (JavaScript)
- 请求/响应封装
- 错误处理
- 重连机制

**为何第三**：
- 需要 Local JAR 的 HTTP/WebSocket 服务
- 前端所有功能都依赖此通信层
- 是前后端交互的桥梁

**实施建议**：
1. 第 1 天：HTTP 客户端封装
2. 第 2 天：WebSocket 客户端封装 + 重连逻辑
3. 第 3 天：集成测试 + 错误处理完善

**验收标准**：
- [ ] HTTP 请求正确封装
- [ ] WebSocket 自动重连
- [ ] 错误统一处理
- [ ] 支持请求取消

---

#### 💾 Task 004: 数据库服务 (12h)

**目标**：实现三模式数据库服务

**产出**：
- Full 模式：SQLite JDBC
- Light 模式：SQLite WASM
- Pure 模式：IndexedDB
- 统一的数据库 API

**为何第四**：
- 需要通信层来与 Local JAR 交互
- 认证系统需要数据库存储用户信息
- 插件系统需要数据库存储插件数据

**实施建议**：
1. 第 1 天：设计统一 API + Full 模式实现
2. 第 2 天：Light 模式 (WASM) 实现
3. 第 3 天：Pure 模式 (IndexedDB) + 模式自动切换

**关键技术**：
- SQLite WASM 集成
- IndexedDB API 封装
- Promise/async 统一接口

**验收标准**：
- [ ] 三种模式都能正常工作
- [ ] API 接口一致
- [ ] 自动模式检测和切换
- [ ] 数据迁移支持

---

#### 🔐 Task 005: 认证系统 (8h)

**目标**：实现用户认证和权限管理

**产出**：
- 本地用户管理

- 首次配置流程

**为何第五**：
- 需要数据库来存储用户信息

- 同步功能需要用户身份

**实施建议**：
1. 第 1 天上午：本地用户管理 + JWT 实现
2. 第 1 天下午：权限系统
3. 第 2 天：首次配置 UI + 集成测试

**验收标准**：
- [ ] 用户注册/登录正常
- [ ] JWT Token 正确生成和验证
- [ ] 权限检查生效
- [ ] 首次配置流程友好

---

#### 🔌 Task 006: 插件系统 (12h)

**目标**：建立插件框架

**产出**：

**为何第六 (最后)**：

**验收标准**：

## 🎯 关键路径分析

### 主关键路径 (最长路径)

```
完整协作版本的关键路径：

Phase 0 全部任务 (68h, 线性)
   ↓
Phase 1 Task 001 前端框架 (16h)
   ↓
Phase 2 Task 001 Sync Server (24h)
   ↓
Phase 2 Task 002 Sync Engine (20h)
   ↓
Phase 2 Task 003/004 插件 (16h, 取最长)

总关键路径: 68 + 16 + 24 + 20 + 16 = 144 小时 (约 18 工作日)
```

## ⚠️ 风险与缓解

### 风险 1: Phase 0 耗时超预期

**影响**：🔴 高 - 阻塞所有后续任务

**概率**：🟡 中等 - Phase 0 技术复杂度较高

**缓解措施**：
1. Phase 0 指派最资深开发者
2. 每个任务完成后立即测试，不留技术债
3. 准备 10-20% 的时间缓冲
4. 及时识别阻塞问题，寻求外部支持

---

### 风险 2: 插件系统设计缺陷

**影响**：🔴 高 - 所有插件需要重构

**概率**：🟡 中等 - 第一次设计可能不完善

**缓解措施**：
1. Task 006 完成后，先开发一个简单插件验证
2. 在 Phase 1 早期发现问题及时调整
3. 保持插件 API 的向后兼容性
4. 详细的插件开发文档

---

### 风险 3: 同步冲突处理复杂

**影响**：🟡 中 - Phase 2 延期

**概率**：🔴 高 - 分布式同步本质复杂

**缓解措施**：
1. 先实现简单的"最后写入者获胜"策略
2. 逐步增强冲突检测和解决
3. 提供手动解决冲突的界面
4. 详细的同步日志和诊断工具

---

### 风险 4: WebAssembly 兼容性问题

**影响**：🟡 中 - Light 模式不可用

**概率**：🟡 中等 - 不同浏览器支持差异

**缓解措施**：
1. 优先保证 Full 模式稳定
2. Light 模式作为增强功能
3. 提供降级到 Pure 模式的方案
4. 针对主流浏览器充分测试

---

### 风险 5: 跨平台兼容性

**影响**：🟡 中 - 部分平台不可用

**概率**：🟡 中等 - Windows/Mac/Linux 差异

**缓解措施**：
1. Phase 0 早期在三个平台测试
2. 使用 Java 标准 API，避免平台特定代码
3. 文件路径使用统一处理
4. CI/CD 中包含多平台测试
